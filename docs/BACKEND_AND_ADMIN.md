# بک‌اند پیشنهادهای سفر و تنظیمات API (محیط آزمایشی)

## اجرا
- محلی: `npm run build && npm run build:server && PORT=3100 node server/dist/index.js` (فرانت ساخته‌شده و `/api/*` از یک سرویس).
- توسعه: `npm run dev` (Vite، پروکسی `/api` به پورت ۳۰۰۰) و `PORT=3000 node server/dist/index.js`.
- تست: `npm test` (کلاینت)، `npm run test:server` (سرور، با fetch ساختگی؛ هیچ تماس واقعی با Gemini/جست‌وجو انجام نمی‌شود).
- `railway.json`: build = `npm run build && npm run build:server`، start = `npm run start:api`. بازگشت: `buildCommand: npm run build`، `startCommand: npm start`.

## ذخیره‌سازی (آزمایشی)
فایل JSON در `DATA_DIR` (پیش‌فرض `data/`). روی Railway بدون Volume با هر استقرار پاک می‌شود. رابط `Store` (server/src/store/types.ts) async است و طرح PostgreSQL متناظر در `server/migrations/001_init.sql` آماده است؛ برای انتقال فقط باید یک پیاده‌سازی `Store` برای PostgreSQL نوشت (هنوز نوشته/آزمایش نشده).

## متغیرهای محیطی
| متغیر | کاربرد |
|---|---|
| `GEMINI_API_KEY` | کلید Gemini (اولویت بر کلید واردشده از رابط) |
| `TAVILY_API_KEY` | جست‌وجوی وب (Tavily) برای منبع‌یابی |
| `UNSPLASH_ACCESS_KEY` | جست‌وجوی تصویر Unsplash، فقط Access Key (Wikimedia بدون کلید) |
| `SECRETS_ENCRYPTION_KEY` | (≥۱۶ نویسه) فعال‌کنندهٔ ذخیرهٔ رمزنگاری‌شدهٔ کلید از صفحهٔ «تنظیمات API» |
| `ADMIN_TOKEN` | (≥۱۶ نویسه) اگر تنظیم شود همهٔ `/api/admin/*` به `Authorization: Bearer` نیاز دارد |
| `ADMIN_OPEN=true` | فقط تست: در production بدون ADMIN_TOKEN دسترسی بازِ ادمین را روشن می‌کند |
| `DATABASE_URL` | نشانی PostgreSQL (مثلاً Neon رایگان: `postgresql://…?sslmode=require`). اگر تنظیم شود همهٔ دادهٔ مدیریت (پیشنهادها، تنظیمات، کلیدهای رمزنگاری‌شده، رویدادها) در PostgreSQL ماندگار می‌شود و جدول‌ها هنگام شروع خودکار ساخته می‌شوند؛ وگرنه فایل JSON آزمایشی |
| `DATA_DIR` | مسیر ذخیرهٔ آزمایشی (Volume برای ماندگاری) |
| `DATABASE_URL` | فعلاً فقط برای `/api/ready`؛ هنوز دادهٔ پیشنهادها در PostgreSQL نیست |

## امنیت (وضعیت فعلی)
- هنوز **ورود ادمین واقعی نیست**. در development دسترسی بازِ آزمایشی است؛ در production بدون `ADMIN_TOKEN` یا `ADMIN_OPEN=true` همهٔ `/api/admin/*` با ۵۰۳ بسته است.
- ذخیرهٔ کلید از رابط در production بدون `ADMIN_TOKEN` مسدود است. کلیدها هرگز در پاسخ API (فقط ۴ نویسهٔ آخر)، لاگ یا فایل‌های build نمی‌آیند.
- پیش از انتشار عمومی: احراز هویت واقعی + نقش‌ها + ثبت اقدامات مدیر.

## چرخهٔ پیشنهاد
draft → pending_review → approved → published (و rejected با دلیل، archived). انتشار فقط با تصویر اصلیِ «تأییدشده» دارای مجوز و بدون پیشنهاد منتشرشدهٔ هم‌نام. ویرایش متنِ منتشرشده، انتشار را لغو می‌کند. هر ویرایش یک نسخهٔ جدید می‌سازد (مقایسه و بازگردانی در پنل).

## تحلیل رفتار و تبلیغات (تصمیم محصول)
- **رضایت‌ها (نسخهٔ سیاست `2026-10-v5`):** تحلیل ناشناس و تبلیغات شخصی‌سازی‌شده پیش‌فرض روشن‌اند و پنجرهٔ رضایت ندارند (با `source: default` ثبت می‌شوند). **اعلان و موقعیت پیش‌فرض ندارند و از مجوز واقعی مرورگر/سیستم‌عامل خوانده می‌شوند**: مجوز داده‌شده = رضایت (`source: permission`)، رد/پرسیده‌نشده/برداشته‌شده = بدون رضایت؛ فقط هنگام تغییر رکورد جدید نوشته می‌شود (`tracker.syncPermissions`، همگام‌سازی در `src/lib/permissionSync.ts` هنگام شروع، بازگشت به برنامه و تغییر مجوز). اگر مرورگر پاسخ قابل‌اعتماد ندهد (`unknown`) چیزی تغییر نمی‌کند. با برداشتن مجوز موقعیت، مختصات و آب‌وهوای ذخیره‌شده از دستگاه پاک می‌شود. رکوردهای «روشنِ» قدیمیِ اعلان/موقعیت نادیده گرفته و با رکورد اصلاحی جایگزین می‌شوند (سرور هم برای این دو نوع فقط `source=permission` را معتبر می‌داند). ردیف «حریم خصوصی و رضایت» از تنظیمات برداشته شده؛ `/privacy` با آدرس مستقیم کار می‌کند. «درخواست حذف داده‌ها» نصب جدید را با تحلیل و تبلیغات **خاموش** شروع می‌کند تا ثبت داده خودبه‌خود از سر گرفته نشود. هنوز نبود: اجرای درخواست حذف در سرور (فقط محلی ثبت می‌شود)؛ حذف کاربر از پنل، رویدادها و رضایت‌هایش را هم پاک می‌کند.
- **پنل کاربران و رویدادها:** رویدادها و رضایت‌ها با شناسه‌های نصب (`anonymous_ids`) به هر کاربر وصل می‌شوند. جزئیات کاربر: رفتار (مقصدها، علاقه‌مندی‌ها با بازپخش افزودن/حذف، علایق با همان امتیازدهی کلاینت، فصل‌ها، کلیک پیشنهاد)، رضایت فعلی هر نوع، تاریخچهٔ رضایت و رویدادهای صفحه‌بندی‌شده. آمار داشبورد از رویدادهای ۳۰ روز اخیر (سقف ۵۰ هزار رویداد، کش ۳۰ ثانیه) و «بیننده» = شخص یکتا. محدودیت: پروفایل هر کاربر از ۵۰۰۰ رویداد تازه‌اش محاسبه می‌شود و فهرست کاربران برای هر ردیفِ صفحه یک کوئری می‌زند؛ بالای چند ده هزار کاربر باید تجمیع در SQL انجام شود. پیش‌نمایش مخاطب فقط شمارش است و بدون رکورد رضایت تبلیغاتی، کاربر «بدون رضایت» حساب می‌شود.
- جریان: رویداد → صف محلی (localStorage) → `POST /api/events` هنگام اتصال (بازگشت اینترنت، دیده‌شدن برنامه، هر ۶۰ ثانیه، عقب‌نشینی نمایی). رکوردهای رضایت (از جمله لغو) همراه می‌روند؛ سرور رویدادِ بعد از لغو را نمی‌پذیرد. `event_id` تکراری دوباره ثبت نمی‌شود.
- پیش از انتشار عمومی، سیاست حریم خصوصیِ قابل‌دسترس برای کاربر و الزامات فروشگاه‌ها/قوانین محل فعالیت را بررسی کنید؛ جمع‌آوری پیش‌فرضِ روشن ممکن است در برخی قوانین یا فروشگاه‌ها نیاز به رضایت صریح داشته باشد.

## اعلان تاریخ
`/settings ← نمایش تاریخ در نوار اعلان`: با کلیک کاربر اجازهٔ اعلان گرفته می‌شود و اعلان با `tag` ثابت نمایش/به‌روز می‌شود (هنگام باز شدن برنامه، بازگشت به برنامه، نیمه‌شب، و `periodicsync` در مرورگرهایی که اجازه می‌دهند). وب‌اپ نمی‌تواند اعلان غیرقابل‌حذف بسازد؛ برای اعلان واقعاً دائمی نسخهٔ اندرویدی لازم است.


## راه‌اندازی یک‌باره روی Railway بدون Volume
1. در Neon (neon.tech) یک پروژه بسازید و «Connection string» را کپی کنید.
2. در Railway → Variables این‌ها را یک بار بگذارید: `DATABASE_URL`، `SECRETS_ENCRYPTION_KEY` (رشتهٔ تصادفی ≥۱۶ نویسه) و `ADMIN_OPEN=true` (فقط تست) یا `ADMIN_TOKEN`.
3. از این پس کلیدهای Gemini/Tavily/Unsplash را از صفحهٔ «تنظیمات API» وارد کنید؛ رمزنگاری‌شده در PostgreSQL می‌مانند و با دیپلوی پاک نمی‌شوند.

## محتوای صفحهٔ اصلی (آیا می‌دانستید + موضوع‌های کاشی صفحهٔ دوم)
- ۹ موضوع (`server/src/feed/schema.ts` ⇄ `src/feed/topics.ts`)، هر کدام یک بخش جدا در پنل: «صفحهٔ اول: آیا می‌دانستید» و «صفحهٔ دوم: کاشی موضوعات» (حال‌وهوای امروز، این ماه وقت کجاست؟، پیشنهاد مخصوص تو، این هفته کجا بریم؟، تقویمی که برای سفر زندگی می‌کند، سفرهای کوچک، لیست آرزوها، هر روز یک کشف تازه).
- چرخه: تولید با هوش مصنوعی (جست‌وجوی وب فارسی + انگلیسی ← Gemini ← جست‌وجو و انتخاب خودکار تصویر) ← پیش‌نویس ← تأیید مدیر ← **صف انتشار** ← هر روز (به وقت تهران) یک کارت منتشر می‌شود. ورود به صف نیازمند تصویر اصلیِ دارای مجوز و حداقل یک منبع است.
- ذخیره‌سازی: یک مقدار KV با کلید `feed_v1` (بدون مهاجرت جدید؛ در PostgreSQL و فایل JSON کار می‌کند). API عمومی: `GET /api/feed`؛ مدیر: `/api/admin/feed/*`.
- برای منبع وب «جست‌وجوی وب» را در «تنظیمات API» روشن و کلید Tavily را وارد کنید؛ بدون آن کارت بدون منبع ساخته می‌شود و باید منبع دستی اضافه شود.

## ورود با شماره موبایل (پیامک قاصدک)

ورود با کد یک‌بارمصرف ۶ رقمی. فایل‌ها: `server/src/auth/*` (قاصدک، سرویس ورود، شماره)، `server/src/routes/auth.ts` (عمومی)، `server/src/routes/authAdmin.ts` (پنل)، `src/auth/*` و `src/pages/ProfilePage.tsx` و `LoginPage.tsx` (اپ)، `src/admin/pages/SmsLogin.tsx` (ابزار تست پنل).

### راه‌اندازی (یک‌بار)
1. در **پنل قاصدک** یک یا چند **قالب آماده** بسازید و تأیید بگیرید (از پنل مدیریت ساخته نمی‌شود): نام لاتین (مثل `taghvim-otp`) و متنی که `%param1%` (جای کد) دارد. سپس در پنل مدیریت ← «ورود و ثبت‌نام پیامکی» ← «قالب‌های پیامک» نام هر قالب را اضافه کنید و وظیفه‌اش را بگذارید: «ثبت‌نام و ورود» (الزامی، یکی)، «بازیابی / ریست» (اختیاری؛ بدون آن از قالب ورود استفاده می‌شود) یا «سایر» (با عنوان دلخواه). درخواست کد با `purpose` (`login` | `reset`) قالب مناسب را انتخاب می‌کند. تنظیمات قدیمی تک‌قالبی خودکار به قالب «ورود» تبدیل می‌شود.
2. کلید وب‌سرویس (`apikey`) را در پنل مدیریت ← «تنظیمات API» ← «پیامک قاصدک» وارد کنید (رمزنگاری‌شده روی سرور) یا در متغیر `GHASEDAK_API_KEY` بگذارید. کلید هرگز در کد، build یا پاسخ API نیست.
3. در «ورود و ثبت‌نام پیامکی»: «آزمون اتصال» (اعتبار)، ارسال آزمایشی به شمارهٔ خودتان و بعد تست کامل از خود برنامه (تنظیمات ← ورود با شماره موبایل).
4. اگر قاصدک خطای «آی‌پی نامعتبر» داد، محدودیت آی‌پی حساب را بردارید (آی‌پی خروجی Railway ثابت نیست).

متغیرها: `GHASEDAK_API_KEY`، `GHASEDAK_BASE_URL` (پیش‌فرض `https://api.ghasedaksms.com`؛ مستند قاصدک نشانی `http` نوشته — اگر https جواب نداد، عمداً و آگاهانه عوض کنید؛ کلید در `http` بدون رمزنگاری می‌رود)، `SECRETS_ENCRYPTION_KEY`، `AUTH_DEV_ECHO` (فقط `NODE_ENV=development` و بدون کلید؛ کد را در پاسخ برمی‌گرداند).

### مسیرها
`GET /api/auth/config` · `POST /api/auth/otp/request` · `POST /api/auth/otp/verify` · `GET /api/auth/me` · `POST /api/auth/logout` · `DELETE /api/auth/account`
پنل (زیر محافظ ادمین): `GET /api/admin/sms` · `PUT /api/admin/sms/settings` · `POST /api/admin/sms/test-send` (با `template_id` اختیاری) `| credit`. مسیرهای ساخت/وضعیت قالب حذف شده‌اند.

### ثبت نصب، ثبت‌نام و پروفایل (پنل «کاربران»)
- هر نصب تازه با `POST /api/installations` (شناسهٔ تصادفی `tp-install-id` در مرورگر، جدا از شناسهٔ تحلیل و بدون اطلاعات شخصی) به‌عنوان **مهمان** در پنل ثبت می‌شود.
- ورود با شماره (`/auth/otp/verify` با `installation_id`) همان ردیف را به **ثبت‌نام‌شده** تبدیل می‌کند؛ `PUT /auth/profile` (نام، نام خانوادگی، شهر، ایمیل اختیاری) آن را **پروفایل کامل** می‌کند. کامل = نام + نام خانوادگی + شهر.
- داده در یک کلید KV (`people:v1`، `server/src/auth/registry.ts`). مسیرهای پنل: `GET /api/admin/users`، `/users/stats`، `/users/:id`، `POST /users/:id/disable`، `DELETE /users/:id`. غیرفعال‌سازی ورود و نشست‌ها را می‌بندد؛ حذف حساب (توسط کاربر یا مدیر) ردیف را هم پاک می‌کند.
- محدودیت: آمار رفتاری (نشست، مقصد، علایق) هنوز از برنامه ارسال نمی‌شود و صفر است. جریان «ریست» در سرور آماده است ولی رمز عبوری در برنامه نیست.
- اپ: منوی کناری دکمهٔ «پروفایل» (جای «خروج») دارد؛ صفحهٔ `/profile` هم ورود/ثبت‌نام و هم تکمیل پروفایل را انجام می‌دهد.

### امنیت و محدودیت‌ها
- کد فقط به‌صورت HMAC ذخیره می‌شود؛ ۲ دقیقه اعتبار؛ یک‌بارمصرف؛ ۵ تلاش؛ فاصلهٔ ۶۰ ثانیه و سقف ۵ ارسال در ساعت برای هر شماره (ارسال ناموفق هم حساب می‌شود)؛ سقف نرخ هر آی‌پی.
- نشست: توکن تصادفی، فقط هش آن ذخیره می‌شود؛ کوکی `tp_session` (HttpOnly، SameSite=Lax، در production Secure، ۳۰ روز). درخواست‌های تغییردهنده با Origin غیرهم‌مبدأ رد می‌شوند.
- شمارهٔ کامل به کلاینت برنمی‌گردد (فقط ماسک‌شده)؛ گزارش ارسال پنل هم فقط شمارهٔ ماسک‌شده دارد و هرگز کد را.
- `anonymous_id` فقط وقتی به حساب وصل می‌شود که کاربر به تحلیل ناشناس رضایت داده باشد.
- حذف حساب پیاده است (`DELETE /api/auth/account`)؛ نشست‌های کاربر حذف‌شده خودکار بی‌اعتبار می‌شوند.
- داده روی KV ذخیره می‌شود (با Postgres ماندگار است؛ با فایل JSON آزمایشی با دیپلوی پاک می‌شود). قفل‌ها درون‌پردازشی‌اند: فرض بر **یک نمونهٔ سرور** است؛ با چند نمونه، سقف تلاش/ارسال دقیق نیست و باید به جدول/قفل دیتابیس منتقل شود.
- کلیدهای باقی‌ماندهٔ KV برای شماره‌هایی که هیچ‌وقت تأیید نمی‌شوند پاک‌سازی خودکار ندارند (حجم ناچیز، با سقف نرخ محدود).
